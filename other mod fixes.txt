XPEDIA2 FIXES - MAKE XPEDIA WORK WITH ANY OXCE MOD (NOT ONLY XPIRATEZ)
=====================================================================
Date: 2026-10-01
Tested on: Reaver's X-Com Harmony (OXCE, master xcom1). Your Reaver save, the
research tree, soldiers and crafts (e.g. MASTODON) all load correctly.

INSTRUCTIONS FOR THE AI APPLYING THIS TO MAIN
---------------------------------------------
- Source files changed: src/load.ts (fixes 1-6) and src/ArticleBody.svelte (fix 7)
- Then run `npm run build` to regenerate xpedia.js / xpedia.js.map.
- Leave the port (2601) and build.mjs as they are.
- Leave mods/xpiratez and mods/xpedia as they are (see the notes at the end).
- Fixes 1-5 are all inside loadFromFiles() plus a new helper. Fix 6 is in the
  cache code. The full unified diff is at the bottom of this file. Apply it, or
  reproduce the changes described below.
- XPiratez must keep working. Its metadata has ids, its rules are in Ruleset/
  and its master is "piratez", so all of these fixes are backward compatible.


ROOT CAUSE SUMMARY
------------------
The loader assumed XPiratez's folder habits. Other mods break those assumptions,
so their data was silently skipped and the page showed little or nothing. On top
of that, the browser cache made xpedia keep showing the old XPiratez data.


FIX 1 - Mods without an "id:" in metadata.yml were dropped   [MAIN BUG]
-----------------------------------------------------------------------
Problem: OXCE uses the mod's FOLDER NAME as its id when metadata.yml has no `id:`.
  Reaver's main mod (user/mods/ReaverHarmony/metadata.yml) has no id line.
  Better_Ingame_UI, Damage_notification, XCOM-Terrain-Pack, "reavers fixed
  hitboxes" and others don't either. xpedia stored them all under
  modMetadataById["undefined"], so they never matched the ids in options.cfg and
  were never loaded.
Change:
  - Add a helper:
      function dirName(dir: string) {
        let parts = dir.split("/").filter(p => p);
        return parts[parts.length - 1];
      }
  - When building modMetadataById, use
      let id = data.id != null && data.id !== "" ? String(data.id) : dirName(dir);
      modMetadataById[id] = { ...data, id, dir };
  - Skip metadata that is not an object (`typeof data != "object"`). A missing
    metadata.yml comes back as the 404 page text, which YAML parses into a
    plain string.


FIX 2 - .rul files were only read from a "Ruleset/" subfolder
-------------------------------------------------------------
Problem: OXCE loads every *.rul file anywhere under the mod folder. ReaverHarmony
  has all 37 of its .rul files in the mod ROOT. Many small mods do the same, and
  one uses a misspelled "Rulset/" folder. Old code: rulDir = `${mod.dir}Ruleset/`.
Change:
  - Set mod.rulDir = mod.dir for every mod.
  - Add a recursive scanner and use it in loadRulsFromMods instead of listDir.
    It skips pure asset folders for speed and stops at depth 4:
      const assetDirs = new Set(["language","maps","routes","terrain","resources",
        "sound","sounds","music","units","geograph","geodata","ufograph",
        "ufointro","images","sprites"]);
      async function listRulsRecursive(dir: string, depth = 0): Promise<string[]> {
        let entries = await listDir(dir);
        let ruls = entries.filter(n => n.toLowerCase().endsWith(".rul")).map(n => dir + n);
        if (depth < 4) {
          let subdirs = entries.filter(n => n.endsWith("/") && !assetDirs.has(n.slice(0, -1).toLowerCase()));
          let nested = await Promise.all(subdirs.map(sub => listRulsRecursive(dir + sub, depth + 1)));
          ruls.push(...nested.flat());
        }
        return ruls;
      }
  - loadRulsFromMods now builds entries as { mod, path, modDir }, where path is
    the full path that listRulsRecursive returns.


FIX 3 - Mods with master "*" or "" were dropped
-----------------------------------------------
Problem: The filter kept a mod only if its master was the id of some master mod.
  In OXCE, master "*" means "works with any master", and it is very common
  (Less Dense Smoke, Time Unit Check, Military Ranks, FirstTurnEnemyTUTweak...).
  Also, the old check accepted ANY master that existed on disk, not the ACTIVE
  one, so xcom2/TFTD-only mods could load under xcom1.
Change:
  - activeMaster = the first id in options.cfg's active list whose metadata has
    isMaster: true (fallback "xcom1").
  - A non-master mod is accepted if its master is null, "", "*", activeMaster,
    or "xpedia".


FIX 4 - Mods in standard/ were never scanned
--------------------------------------------
Problem: Only user/mods/ was listed. OXCE also loads mods from standard/
  (XcomUtil_*, UFOextender_*, ...), and several of them were active here.
Change:
  - Also call listDir(`${OXCPath}standard/`, true) and keep only the folders.
  - Candidate dirs = [...standardDirs, ...userModDirs, ...xpediaDirs]. User mods
    come after standard/, so a user copy with the same id wins. Still make sure
    standard/xcom1/ is in the list if the listing missed it.


FIX 5 - Load order did not follow options.cfg
---------------------------------------------
Problem: Mods were re-sorted with a made-up priority (master == xcom1 -> 2, etc.).
  In OXCE, the order of `mods:` in options.cfg IS the load order; later mods
  override earlier ones.
  The language list also had a hard-coded
  `langDirs.splice(1, 0, "/standard/xcom1/Language/OXCE/")`, which assumed xcom1
  was at index 1.
Change - the final active list is, in this order, with duplicates removed and
missing ids dropped:
    1. xpedia's own mods whose master == "xpedia" (common data, lowest priority)
    2. activeMaster
    3. options.cfg active mods, in options.cfg order (non-masters passing Fix 3)
    4. xpedia's own mods whose master == activeMaster (e.g. piratez_xpedia),
       so they sit on top of their mod
  If options.cfg has an active id with no matching folder (for example a zipped
  mod like mui_144-2noz.zip), log a console.warn and skip it.
  Language dirs: for each active mod push `${dir}Language/`. If the mod is a
  master, also push `${dir}Language/OXCE/` right after it.
  If options.cfg is missing, use every discovered non-xpedia mod (same as before).


FIX 6 - The browser cache showed the OTHER game's data
------------------------------------------------------
Problem: Parsed data is cached in IndexedDB ("xpedia" db, store "cache", id 1).
  IndexedDB belongs to the origin http://localhost:2601, and every xpedia install
  uses that same address. After running xpedia in an XPiratez install, running
  it from another game folder loaded the cached XPiratez data and never read the
  new files. That is a big reason it "didn't work" with other mods.
Change:
  - Add cacheKey(): fetch user/options.cfg and the user/mods/ listing. Wrap each
    in Promise.resolve().then(...) because fetchText can be synchronous (fsFile).
    Take just the `mods:` block of options.cfg and return
      `${location.pathname}|${modsBlock}|${userModsListing}`
  - useCache(data, key?) stores { id: 1, key, data }. On "load", if a key was
    passed and it doesn't match the stored key, return null so the data is
    re-read from files.
  - In loadRules: key = await cacheKey(); useCache("load", key); after loading
    from files, call useCache(data, key).
  Side benefit: turning mods on or off in the game now refreshes xpedia
  automatically.


FIX 7 - Every article page was blank (crash in src/ArticleBody.svelte)
----------------------------------------------------------------------
Problem: The entry list loaded, but opening any article (e.g.
  http://localhost:2601/xpedia2/##STR_HEAVY_LASER) showed nothing. The console
  showed:
    TypeError: Cannot read properties of undefined (reading 'STR_HEAVY_LASER')
    TypeError: info.mount is not a function
  ArticleBody.svelte line 75 loops over every renderer type and reads
  rul[key][id]. Some tables (alienRanks, mapScripts, inventorySections) are not
  set up in the Ruleset class and only exist if some mod defines that section.
  XPiratez defines all of them; Reaver Harmony doesn't, so rul[key] is undefined
  and the whole article crashes.
  This was NOT a node_modules / npm install problem.
Change (src/ArticleBody.svelte, line 75), add optional chaining:
  - {#each Object.entries(renderers).filter(([key]) => rul[key][id]) as [key, ren]}
  + {#each Object.entries(renderers).filter(([key]) => rul[key]?.[id]) as [key, ren]}
  The rul[key][id] uses on lines 77/80 are only reached after this filter
  passes, so they are safe.
  (A more thorough alternative: also give alienRanks, mapScripts and
  inventorySections a `= {}` default in the Ruleset class, like the other
  tables around src/Ruleset.ts:1212-1241.)


NOTES (no code change)
----------------------
- Only one xpedia can run on port 2601 at a time. If another copy is running,
  `npm start` fails with "bind: Only one usage of each socket address", and the
  browser keeps showing the OTHER copy's game. Close the other one first.
- Zipped mods are not read (only a console warning). The mUi ones are UI-only,
  so no data is lost.
- Intro.svelte still has XPiratez text and title art. That's cosmetic and left
  alone.
- mods/xpiratez only holds extra XPiratez language strings (master: piratez). It
  loads only when piratez is the active master. It is SAFE TO DELETE in a
  non-XPiratez install, but KEEP it in the main repo for XPiratez users.
- mods/xpedia is xpedia's own common data and UI strings and loads for every
  mod. Do NOT delete it.
